# ADR-0005 — Rate limiting de login com Redis e fallback em memória

- **Status**: Aceita
- **Data**: 21/09/2026
- **Decisores**: Time de desenvolvimento Mesa Justa (com apoio de IA generativa agêntica)
- **Áreas afetadas**: Autenticação, Segurança, Infraestrutura (Redis)

---

## Contexto

O endpoint de login é o principal alvo de brute-force do MVP. O PRD/RNF-02 exige proteção dos dados pessoais segundo a LGPD, e o `auth-setup` definiu sessão via cookie HttpOnly. Precisamos de um mecanismo de rate limit barato e resiliente que não dependa de Redis em todos os ambientes (dev/CI), mas que escale em produção (staging/produção com Redis). A configuração precisa ser ajustável via ambiente para testes E2E (evitar bloqueio acidental durante cenários de login repetidos).

## Decisão

- **Duas dimensões de limite por janela de 15 min**: `EMAIL_MAX_ATTEMPTS` (padrão 10) e `IP_MAX_ATTEMPTS` (padrão 30), ambos configuráveis por variável de ambiente.
- **Sink dupla**: usa Redis (`INCR` + `EXPIRE` + `TTL`) quando `REDIS_URL` estiver definida; caso contrário, cai para **bucket em memória** (Map com reset por janela e limpeza de buckets vencidos acima de 5.000 chaves).
- Contador é registrado apenas **após falha** (`recordLoginFailure`); checagem prévia feita com `assertLoginNotBlocked`. Sucesso limpa a contagem (`clearLoginFailures`).
- O cliente Redis é instanciado lazy e falhas de conexão degradam graciosamente para o sink em memória, sem derrubar o login.

## Alternativas consideradas

| Alternativa | Prós | Contras | Veredito |
|---|---|---|---|
| **Redis com fallback em memória (escolhido)** | Escala em produção; funciona em dev/CI sem infra; tolerante a queda do Redis | Estado em memória é por instância de processo (aceitável para MVP single-instance) | **Aceito** |
| Rate limit apenas em memória | Zero dependência | Perde contadores entre restarts e em múltiplas instâncias | Rejeitado |
| Middleware HTTP genérico (ex.: `express-rate-limit`) | Serializa faixas de IP simples | Não cobre dimensão por e-mail; fora do padrão Next Route Handlers | Rejeitado |

## Consequências

**Positivas**
- Proteção dupla (e-mail + IP) configurável por ambiente; E2E pode sobrepor limites via `.env.e2e`.
- Não bloqueia o fluxo se o Redis cair (degradação graciosa).
- Testável sem Redis: CI roda com sink em memória.

**Negativas / trade-offs assumidos**
- Em múltiplas instâncias sem Redis compartilhado, o limite é por instance (relaxado). Produção deve usar Redis (já previsto no stack).
- Limites padrão conservadores podem exigir ajuste fino com métricas reais.
